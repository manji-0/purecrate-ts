# 型の共有をスコープに入れられるか

作成: 2026-09-27。前提は design/04（目的を「振る舞いの共有」と定義し直した）。

## 0. 結論

- **入れられる。ただし「境界の型」として入れる。** 型定義だけを出す機能（ts-rs の領域）は目標にしない。目標にするのは、共有した振る舞いが受け取り、返す値を、Rust サーバーの JSON（serde）と行き来させるコーデックの生成である。
- 理由は二つある。第一に、振る舞いを共有しても、TS 側の値は多くの場合サーバーの JSON から来る。今はその変換を手書きするしかなく、本ツールが消すと約束した「二重実装のずれ」がそこに残る。第二に、型だけの生成で ts-rs と正面から競うと、ジェネリクスも serde 属性も外部型も扱えない劣った製品になる。
- **設定しだいで今すぐ誤った型が出る。** `#[serde(rename_all = "camelCase")]` などの serde 属性は黙って無視される。生成した型をワイヤ形式の型として使うと、フィールド名が食い違う（§2.3）。どの方針を採るにしても、serde 属性の検出と拒否は先に入れるべきである。

## 1. 「型の共有」の三つの意味

| 意味 | 内容 | 代表 | 本ツールとの関係 |
| --- | --- | --- | --- |
| (a) 型定義の生成 | Rust の型から TS の型宣言を出す。実行時の検査はない | ts-rs、specta、tsify | 副産物としては既に可能（§2.1） |
| (b) ワイヤ表現との整合 | serde が出す JSON と TS の値を相互に変換し、検証する | zod_gen（スキーマ）、手書きのデコーダ | **未対応。振る舞い共有の実用上の穴** |
| (c) 振る舞いと型の同一ソース | 遷移関数とその引数の型を同じ Rust から出す | Crux（WASM 経由） | 現在の対象 |

design/04 の再定義は (a) との差別化だった。しかし (b) がなければ、(c) の生成物にサーバーのデータを渡す経路が手書きのまま残る。

## 2. 現状の事実（2026-09-27 に確認）

### 2.1 型だけの crate は今でも通る

struct と enum だけの crate も受理され、型と companion（`of` とバリアントのコンストラクタ）が出る。(a) は追加実装なしで「できる」。ただし次の理由で、DTO 用途ではほとんど使えない。

- ジェネリクス（`Page<T>`）、外部型（`chrono`、`uuid`、`rust_decimal`）、`HashMap` を受理しない。
- `i64` が `bigint` になる。serde_json は `i64` を JSON の数値として出すので、ts-rs 利用者が期待する `number` とは異なる。

### 2.2 生成する値の表現は serde の既定の JSON と違う

生成物の値は kamae 形（`kind` による判別ユニオン）で、serde の既定（外部タグ）とは別物である。

| Rust | 生成 TS の値 | serde_json の既定 | `#[serde(tag = "kind")]` の場合 |
| --- | --- | --- | --- |
| unit バリアント `Inc` | `{ kind: "Inc" }` | `"Inc"` | `{"kind":"Inc"}`（一致） |
| newtype `Add(i32)` | `{ kind: "Add", content: [1] }` | `{"Add":1}` | 中身が struct のときだけ可。`i32` は serde が拒否する |
| tuple `P(i32, i32)` | `{ kind: "P", content: [1, 2] }` | `{"P":[1,2]}` | serde が拒否する |
| struct `Move { dx }` | `{ kind: "Move", dx: 1 }` | `{"Move":{"dx":1}}` | `{"kind":"Move","dx":1}`（一致） |
| `i64` / `u64` | `bigint` | 数値 | 数値 |
| `Option<T>` | `T \| null` | `null` またはその値 | 同左 |
| `Result<T, E>` | `{ kind: "Ok", value }` | `{"Ok":v}` | （属性は Result に付かない） |
| `()` | `undefined` | `null` | `null` |

### 2.3 serde 属性は黙って無視される

`#[derive(Serialize)] #[serde(rename_all = "camelCase")] pub struct State { pub total_count: i64 }` を与えると、エラーなしで `total_count: bigint` が出る。サーバーの JSON は `totalCount` である。v0 の「構文を黙って落とさない」方針に反する。

**対応済み（TODO 21）**: item、バリアント、フィールド、メソッドに付いた `#[serde(...)]` を位置つきで拒否する。`#[cfg]` と `#[cfg_attr]` も拒否する（生成物は条件付きコンパイルを再現できず、`cfg_attr` は serde 属性を差し込めるため）。`#[cfg(test)]` の item は通常のビルドに存在しないので読み飛ばす。`derive`、`doc`、lint 属性は通す。

### 2.4 64 ビット整数は `JSON.parse` で精度を失う

`JSON.parse('{"a":9007199254740993}').a` は `9007199254740992` になる。Node 24 では、reviver の第 3 引数から数値の元の文字列を読めるので、`BigInt` へ無損失で変換できる。書き出しにも `JSON.rawJSON` が使える。どちらも ES2025 の JSON.parse source text access。Hermes（React Native）が対応しているかは未確認である。対応していなければ、小さな JSON パーサを生成物に含める必要がある。

### 2.5 serde は vendor にない

`vendor/` にあるのは syn と、その依存（proc-macro2、quote、unicode-ident）だけ。serde_json と突き合わせる差分テストを書くには、serde、serde_derive、serde_json を vendor に追加する必要がある（オンライン作業が一度だけ要る）。

## 3. 選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A. 対象外と明言 | DTO は ts-rs に任せ、変換は利用者が書く | 追加コストなし | 手書きの変換がずれの温床として残り、中心の約束が端で破れる。ts-rs の型と生成物の型は形が違う（§2.2）ので、両者の間の変換も要る |
| B. 型だけの生成を正式機能にする | serde 属性、ジェネリクス、外部型へ対応を広げる | 大きな隣接市場（ts-rs の直近ダウンロード 620 万）に入れる | ts-rs、specta と正面から競合する。subset の制約（ジェネリクスなし）と両立しない。振る舞い共有という差別化点を薄める |
| C. 境界コーデックの生成 | 公開する各型に `decode`（JSON テキスト → `Result<T, DecodeError>`）と `encode`（T → JSON テキスト）を生成する。serde_json の既定表現と一致させ、差分テストで保証する | ts-rs は型だけで実行時の検査がなく、zod_gen はスキーマが振る舞いと切れている。C は「検証済みのデコーダ + 型 + 振る舞い」が同じソースから出る。kamae の「境界でパースする」と一致する | 中規模の実装（64 ビット整数の無損失パース、外部タグの変換、エラー型）。serde の vendor 追加が要る |
| D. 表現の収束 | Rust 側に `#[serde(tag = "kind")]` を要求し、TS の値表現と JSON 表現を同じにする | 変換がほぼ不要になり、検証と `bigint` の扱いだけが残る | サーバーの API 形式を変えさせる。tuple バリアントと、プリミティブを包む newtype バリアントは serde が拒否する |

## 4. 評価

- **B は採らない。** 需要が大きいのは (a) だが、DTO crate の多くはジェネリクス、外部型、serde 属性を使っており、今の subset ではほぼ受理できない。受理範囲を広げると、「Rust と同じ結果を返すことを検証できる」という核と無関係な方向へ実装が流れる。
- **A は中心の約束を損なう。** 状態機械の用途でも、初期状態やサーバーとの同期で JSON を受け取る。そこを手書きさせるなら、生成で得た安全性が境界で失われる。
- **C が差別化になる。** ts-rs の利用者が抱えている「型は合っているのに実行時の値が違う」問題を、振る舞いと同じ差分テストの枠組みで解ける。次の順で差分テストを組める。Rust で値を作り、serde_json で書き出し、TS の `decode`、関数呼び出し、`encode` を通して、Rust の serde_json で読み戻して比べる。壊れた JSON は、serde がエラーにするときに TS も `Err` を返すことまで確かめられる。
- **D は C の特殊ケース。** `tag = "kind"` の型は表現が一致するので、生成するコーデックが小さくなる。新規プロジェクトでは推奨の形にできる。C の後に追加する。

## 5. 推奨

**決定（2026-09-27）**: C（境界コーデック）を採る。着手順は 1（serde 属性の拒否）、次に design/04 §4-3（`?`・`if let`・`Option`・`let mut`）とする。

1. **すぐやる（小）：serde 属性の検出と拒否。** `#[derive(Serialize, Deserialize)]` だけなら通す。`#[serde(...)]` は、対応するまで位置つきで拒否する。§2.3 の「黙って誤る」状態をなくすためで、どの方針でも必要。
2. **受理率の計測（design/04 §4-2）に DTO 系の crate も含める。** C の投資判断に使う。ジェネリクスと外部型で大半が落ちるなら、C の対象は「状態機械の State と Event」に絞る。
3. **C を実装する。** serde の既定表現だけを対象に、`decode` と `encode`、64 ビット整数の無損失パース、serde_json との差分テストを作る。
4. **受理率のデータ次第で、`tag = "kind"`（D）、`rename_all`、`rename` に対応する。**

目的文は design/04 §1.2 を次のように広げる。

> Rust で書いた純粋なドメインロジックの **振る舞い** と、それが受け渡す値の **境界表現（serde JSON）** を、WASM なしで素の TypeScript に写し、どちらも Rust と観測上同値であることを機械的に検証できる状態を作る。

成功条件として次を追加する。

- 受理した公開型のすべてについて、serde_json → `decode` → `encode` → serde_json の往復で値が一致すること（差分テスト）。
- `2^53 + 1` のような 64 ビット整数の境界値を失わないこと。
- serde が拒否する JSON は、`decode` も `Err` を返すこと。

## 6. 未決の問い（2026-09-27 時点）

- `decode` の入力を JSON テキストにするか、`unknown`（パース済みの値）にするか。64 ビット整数の精度を守るにはテキストが要る。既存の fetch ラッパーとの相性は `unknown` のほうが良い。
- Hermes は JSON.parse の source text access に対応しているか。非対応なら、生成物に JSON パーサを持たせる。
- 非有限の浮動小数（serde_json は `NaN` を `null` として書き出す）を型で拒否するか、往復の非対称として文書化するか。
- `Option` のフィールドが欠けていたとき（serde は `None` として扱う）を、`decode` でも同じく受け付けるか。

## 7. 問題の切り分け（2026-09-28）

実装には入らない。サーバーの JSON を生成した関数に渡す問題は、三層に分かれる。どれも今は手書きになる。

### 7.1 渡したいもの

対象は、新しく書く状態機械の公開した状態と事象である。クライアントはサーバーの JSON を受け取り、`step(state, event)` に渡す。イベントの列は状態の中に積まない（design/02 §1.1）。列の伸長は、この境界の問題ではない。

`step` 自体は JSON を読まない。kamae では、境界でパースした値だけがドメインに入る。

### 7.2 形が違う

生成物の値は `kind` の内部タグである。serde の既定 JSON は外部タグである（§2.2）。`JSON.parse` の結果は、生成された状態の型ではない。

`#[serde(...)]` は拒否する（§2.3）。黙って別名の JSON を受理することはない。コーデックが対象にするのは、属性なしの serde 既定だけである。

### 7.3 数が違う

JSON の数値は、ブランドのない `number` である。`i32` のフィールドは `I32`、`f64` は `F64`、`i64` は `I64`（`bigint`）である。形が一致していても、`JSON.parse` の数をそのままフィールドには入れられない。

`i32` は `Int.i32.of` で範囲と整数性を検査できる。`i64` は `JSON.parse` が 2^53 を超えると精度を落とす（§2.4）。テキストから読む必要がある（§7.6 の 1）。`f64` の非有限値は、serde_json が `NaN` を `null` として書く。

### 7.4 この問題ではないもの

- 遷移関数の中で JSON をパースすること。
- 型宣言だけを ts-rs の代わりに出すこと（§4 の B）。
- 状態の中の `Vec` を伸ばすこと。
- `#[serde(rename_all)]` 付きの既存 API をそのまま読むこと。属性は拒否している。

### 7.5 方針（2026-09-28）

スキーマライブラリは核に入れない。`packages/boundary`（パッケージ名 `purecrate`）がブランド型と `Int.*.of` を持つ。生成パッケージはここから `I32` などを輸入する。

zod、valibot、arktype は別パッケージの薄いアダプタである。三つを同時には依存しない。

`--schema zod|valibot|arktype` を付けたときだけ、公開した struct と enum のワイヤ用スキーマを `src/purecrate-wire.ts` に出す。形は serde の既定 JSON で、結果はドメインのブランド型である。指定していないライブラリのスキーマは出さない。

arktype は、morph を含むオブジェクトを一つの和にすると実行時に拒否する。enum はバリアントを一つずつ試す。arktype のスキーマは、どれも `unknown` からの morph で、`Wire<T>` と型を注釈する。JSON の形は初回の読み取りで組み立てる（`memo`）。これで、再帰する型や、ファイルの後ろで宣言するスキーマも参照できる。以前は再帰する struct を一つの `type.module` に置いていたが、モジュールの外の enum を参照できず、`Box` の中の struct を初期化前に読んで、import した時点で `ReferenceError` になっていた（2026-09-28 に置き換え）。

生成したワイヤ用スキーマは、TypeScript 6 と 7 の `tsc --strict` を通す。型の形を網羅した fixture（`crates/cli/tests/fixtures/wire_shapes.rs`）を三つのライブラリで生成し、型検査と、serde の既定 JSON の読み取り・拒否を node で確かめている（`crates/cli/tests/wire.rs`）。zod と valibot の struct は、パースしたオブジェクトをそのまま返さず、フィールドごとに組み立てる。値が `undefined` になりうるフィールド（`()`）を、スキーマの推論が省略可能にするからである。

### 7.6 この実装で決めたこと

1. スキーマの入力はパース済みの値である。`i64` / `u64` は、安全な整数（±(2^53−1) 以内）の JSON の数値、`bigint`、数字の文字列を受ける。範囲の外はスキーマの失敗として返し、例外にしない。2^53 を超える数値は `JSON.parse` が丸めた後なので、拒否する。丸めた値は必ず安全な範囲の外に出るので、誤った値を黙って読むことはない。serde_json が書く大きな整数を落とさずに読むには、`purecrate` の `parseJson(text)` で JSON テキストを読む。`JSON.parse` の reviver に渡るソーステキスト（Node 21 以降）から、安全な範囲の外の整数リテラルだけを `bigint` にする。serde_json は `f64` を必ず `.` か指数付きで書くので、`f64` の値は変わらない（2026-09-28）。
2. 対象は、公開した struct と enum の全部である。
3. 欠けた `Option` フィールドは `None` である。JSON の `null` も `None` である。serde の既定と同じ。
