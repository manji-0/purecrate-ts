# Equivalence

Status: current (2026-10-15, 0.21.0)

<!-- derived-from ./00-overview.md#1-claim -->

## 1. Definition

For an accepted public function `f` and its generated counterpart `f'`, and for every Rust value `x` in its domain with TS representation `x'`:

| Aspect | Requirement |
| --- | --- |
| Return value | `f(x)` and `f'(x')` are equal as values |
| Types | TS types represent the Rust types exactly (`i64` → `bigint`, width brands) and pass `tsc --strict` |
| Expected failure | `Err` has the same variant and the same payload |
| Unexpected failure | Where Rust panics, TS throws `Panic` with Rust's message (arithmetic, indexing, and the panics of §7.17) |

**The reference is the Rust debug build.** Overflow and division by zero panic there, so they throw in TS. Release-mode wrapping is not matched. This was chosen over rejecting every operation that may panic (too narrow) and over accepting only `checked_*` APIs (too awkward), and it agrees with kamae's "the unexpected is an exception".

The main use of the output is a server that shares the same types and functions. That server is built with `--release`, where `overflow-checks` is off by default, so on overflow Rust wraps while TS throws: the two sides disagree on exactly the inputs where it matters. Equivalence with the server holds only when the crate (or workspace) sets `[profile.release] overflow-checks = true` (and `debug-assertions` if anything depends on them). `check` and `build` refuse a crate whose release profile does not; `--allow-overflow-wrap` accepts the difference with a warning. A single `.rs` file with no manifest has no profile to read and is not refused.

## 2. Domain

The domain is **the image of Rust values under the TS representation**, not every value TS can construct. For `x'` outside the image nothing is promised.

| Outside the image | Why |
| --- | --- |
| `5 as I32`, `"x" as Email`, out-of-range or non-integer `number`s | Brands exist only in types. Values entering from outside go through `Int.i32.of` or a wire schema |
| Values of closed types not returned by public functions | See §4 |
| Strings with lone surrogates | Not a Rust `String`. A `pub` function panics on one in a string parameter (§6), and a wire schema refuses one |
| Objects mutated in place | The output is not `Object.freeze`d, and `Readonly` stops only assignment through the type: `Object.assign(Version.preRelease(v), [..])` or `Object.assign(rule, { interval: .. })` compiles with no cast. Any mutation is visible through aliases that Rust would not share (an accessor returns the value it holds, not a copy, and a caller's array passed in is the one kept), and can break a closed type's invariant |
| Reading the original argument after the call | Rust moved it; TS still has it. Not promised either way |

## 3. Known non-equivalences

| Gap | Detail |
| --- | --- |
| `usize` ≥ 2^53 | Rust is fine up to 2^64; TS throws above 2^53−1. Lengths and indices do not reach this range. `bigint` was rejected because it does not mix with arrays and loops. The integer methods work in Rust's 64 bits on `usize` (`checked_add` is `None` only past 2^64, `wrapping_sub(0, 1)` is 2^64−1) and throw where that result is above 2^53−1 |
| Recursion depth | Measured 2026-09-28 (list length, Node 24.21, macOS): TS passes 10,000 levels and throws `RangeError` at 12,000. Rust debug passes 50,000 on the main thread and **aborts** at 100,000 (not a catchable panic; test threads have 2 MB). Even "both fail" does not hold |
| JSON nesting depth | serde_json rejects nesting deeper than 128; the wire schemas have no limit |
| Release wrapping | Not matched, unless `[profile.release] overflow-checks = true` (the server's usual `--release` build wraps; generated TS always panics). `check` refuses a crate whose release profile leaves the default, unless `--allow-overflow-wrap` |
| Non-finite `f64` over JSON | serde_json and `toJson` both write `NaN` and infinities as `null`, and neither reads `null` back as a float. Same bytes, same asymmetry ([04 §6](./04-wire.md#6-reading-and-writing-text)) |
| `u128` literals and consts ≥ 2^127 | Literals and folded constants are held as `i128`, so a `u128` literal or `const` at 2^127 or above is refused with a message (in a function, build it as `!0` or by shifts); values of the type reach 2^128−1 at run time |
| `sort_by` with an inconsistent comparator, or a key or comparator that panics | Rust's sort may panic ("user-provided comparison function does not correctly implement a total order") or leave any order; JS `sort` never panics and leaves its own order. Std and V8 also compare pairs in different orders, so where comparing may panic more than one way (an overflow and a division by zero, on different elements), past about 20 elements the first panic can differ. Equal for a comparator that is a total order and cannot panic, as `cmp` and `then` chains on the elements are; stability over equal elements holds |
| Unicode-table methods | `to_lowercase` / `to_uppercase` (§7.21): equivalence holds only for code points assigned in both toolchains' Unicode versions (both 17.0 as of 2026-09-27) |

## 4. Closed types

<!-- derived-from #2-domain -->

In Rust, a struct with any non-`pub` field cannot be built by a literal outside its crate; values come only from public functions. That rule is carried over. Verified by `crates/cli/tests/it/closed_equivalence.rs`.

| Rust struct | Kind | TS companion | Values come from |
| --- | --- | --- | --- |
| Any non-`pub` field (`pub(crate)` and `pub(super)` count as non-`pub`), including newtypes | **closed**, branded by a declaration its own file makes and does not export (a newtype by a `unique symbol` key, `{ readonly [Meters$brand]: true }`; a struct by a class with a `private` member, `Line$brand`, which an object spread does not copy), so no literal or spread outside the package can be one | no `of` | public functions, or the wire (§4.2) |
| All fields `pub` | **open** | `of` | anyone, as in Rust |

Which function is the "checked constructor" is not inferred. Whatever public function returns the type is the way in, whether named `new`, `parse`, or `try_from`.

### 4.1 Internal names

- **`unsafeMakeEmail`.** The generator builds values of a closed type through an internal `unsafeMakeEmail`, marked `@internal` (and left out of the `.d.ts` by `stripInternal`). It is exported from the type's file but not from `index.ts`; `exports` exposes only the index, so an installed package cannot deep-import it. When the sources are vendored, `import { unsafeMakeEmail } from "./gen/src/email.ts"` reaches it and builds a value without a cast. Closedness is that convention plus the consumer's `as` lint ([03 §5.5](./03-output.md#55-closed-types)), not a type-level seal. The name is checked against the crate's top-level names and numbered where one has it (`unsafeMakeEmail2` beside a `fn unsafe_make_email`). Until 0.8.0 it was `Email$of`.
- **Non-`pub` methods** are not on the companion either. They are emitted as `emailUnchecked`, `@internal`, exported from the file but not from `index.ts`, like `unsafeMakeEmail` and named the same way (until 0.8.0, `Email$unchecked`). Otherwise a private `fn unchecked(raw) -> Email` would let TS callers build what Rust callers cannot (a hole found by real use, [CHANGELOG 0.1.0](../CHANGELOG.md#rationale-the-first-release)).

### 4.2 The domain of a closed type

Values returned by public functions, or read from the wire. The wire reads by shape as serde's derive does, or, with `#[serde(try_from = "T")]`, through the checked constructor ([04 §5](./04-wire.md#5-closed-types-on-the-wire)). Rust has the same set, so correspondence is kept.

### 4.3 Not closed at runtime

`as` still works, fields are readable, and objects are not frozen, so `Object.assign` changes a closed value's fields with no cast (the brand keeps out a literal or a spread, not mutation in place). Freezing at construction would be shallow (an array or a nested value stays open) and cost every hot path; classes with `#private` fields would close it, but break idiomatic values, JSON, and structured cloning.

### 4.4 Validation layers

| Layer | Question | Owner |
| --- | --- | --- |
| **Shape** | Is this JSON an `Order`? | the wire schema |
| **Meaning** | Is this an `Email`? | shared, via closed types and checked constructors |
| **Screen** | Wording, i18n, which field | the caller |

Error messages are therefore not shared; the `Err` variant and payload are. A common error type with field paths will be introduced only when the same field-assignment table is duplicated across examples.

## 5. Numbers

`check::accept` infers a type for every expression and rewrites arithmetic before printing.

| Rust | Generated TS | Details |
| --- | --- | --- |
| integer `+ - * / %`, unary `-` | `Int.<ty>.add(a, b)` etc. | §5.2 |
| integer `& \| ^`, `!`, `<< >>` | `Int.<ty>.and(a, b)`, `or`, `xor`, `not`, `shl`, `shr` | §5.3 |
| `f32` arithmetic | `Math.fround(a op b)`. `f32` literals are rounded once from decimal by the converter (not via `f64`) | |
| `f64` arithmetic | JS operators | |
| `i64` / `u64` / `i128` / `u128` literals | `5n` | 128-bit integers are `bigint`s as 64-bit ones are, with `Int.i128` / `Int.u128` checking 128 bits (`wide_int_equivalence.rs`) |
| widening `i64::from(x)` | value unchanged; `BigInt(x)` when crossing to `bigint` | |
| byte string `b".."` | `Str.bytes("..")` where the bytes are UTF-8 (the same bytes `"..".as_bytes()` gives), else an array of byte literals | as a `&[u8]` const or in an expression; `wide_int_equivalence.rs` |

Verified by per-operator differential tests: 59 cases, floats included (`arith_equivalence.rs`); bitwise operators and shifts in §5.3.

### 5.1 Type inference

Inference is bidirectional and closed within the expression tree. It does not use rustc's later-use inference (but for a `let` of an unsuffixed integer, §7.22) or the `i32`/`f64` defaults, so an untyped literal is rejected with a request for a suffix or annotation. Comparisons whose result differs between JS and Rust (ordering on `bool`, `==` on a value holding `ParseIntError` or `uuid::Error`, which are opaque here while Rust compares their kinds) are rejected; `String` ordering goes through the runtime (§6.1), and ordering the crate's types, `Option`s, `Vec`s, and tuples through their `cmp` (§7.25). `==` and `!=` on the crate's structs and enums (whose `PartialEq` rustc requires to be derived, as no trait `impl` is in the subset), `Option`, `Result`, `Vec`, and tuples compare part by part as the derived `eq` does: `Eq.deep(a, b)` takes `===` on numbers, `bigint`s, strings, and `boolean`s (NaN unequal to itself, `-0.0` equal to `0.0`, as Rust's `==`), `null` only to itself, arrays element by element, and objects key by key, a variant's `kind` among them. A closed type's brand is a type only, so its value compares as any other. Tested on every pair of a recursive JSON tree's values, structs with float fields, every variant shape, and `Option` / `Result` / tuples of them (`deep_eq_equivalence.rs`).

### 5.2 Integer arithmetic

- **Rule.** `/` truncates. Overflow and division by zero throw Rust's panic message. `-0` is normalized to `0`.
- **Why typed.** Printed as JS operators, `i32` `7 / 2` would be `3.5`, `i32::MAX + 1` `2147483648`, and `1 / 0` `Infinity`, which is what the output computed before the IR had types.

### 5.3 Bitwise operators and shifts

- **Results wrap to the width** and never panic: JS int32 operators, then sign- or zero-extension; `BigInt.asIntN`/`asUintN` for 64 bits.
- **Shift amounts.** An amount of any integer type outside `0..bits`, compared as its whole value (`-1`, `2^32 + 1`), throws `attempt to shift left with overflow`, as a debug build panics. An unsuffixed amount is `i32`, as in rustc.
- **Refused.** `usize`: Rust gives it 64 bits, the TS `number` 53. `& | ^` on `bool`, in favor of `&& || !=`.
- **Verified by** `bits_equivalence.rs`: every width, operator, and amount type, boundary values, compound assignment, RFC 4226 truncation.

### 5.4 Floats

- **Methods.** `floor`, `ceil`, `trunc`, and `abs` are `Math`'s, which IEEE fixes as Rust's; an `f32` result is already an `f32`. `round` is half away from zero, where `Math.round` takes half up: `Int.f64.round` rounds the magnitude and gives the sign back (`x * -1`, so `-0.4` stays `-0.0`). `is_nan`, `is_finite`, `is_infinite` are `Number.isNaN`, `Number.isFinite`, and `Math.abs(x) === Infinity`. `f64::NAN`, `INFINITY`, `NEG_INFINITY` (and `f32`'s) are `Number`'s.
- **Float to integer.** `x as T` truncates toward zero and saturates at `T`'s bounds, NaN to 0, as Rust's `as` has since 1.45: `Int.<t>.castFloat(x)` compares with the bounds as floats (each is exact, or rounds up to the next power of two, which no float below it reaches) and truncates the rest exactly into a `bigint`. Into `usize`, a result above 2^53−1 panics (§3).
- **Integer to float.** `f64::from(x)` from `i8`–`i32` / `u8`–`u32` is exact (the `number` it is); `x as f64` from a 64- or 128-bit `bigint` is `Number(x)`, the nearest double, ties to even, as Rust rounds. `x as f32` rounds once: `Math.fround` of a value below 2^53 (exact as a double), and above that `Int.f32.ofBig`, which rounds the `bigint` to 24 significant bits itself, since rounding to a double first could round twice. `f64` to `f32` is `Math.fround`; `f64::from(x)` from `f32` is the value.
- Tested bit for bit at every half, `-0.0`, the edges of each integer width, 2^24 and 2^53 with their neighbours, and values that round once differently from twice (`float_conv_equivalence.rs`).

## 6. Strings, `char`, `usize`, std methods

<!-- derived-from #3-known-non-equivalences -->

Methods are added one at a time, as examples ask ([07 §1](./07-roadmap.md#1-how-additions-are-chosen)). Two rules hold throughout:

- **Allow-list, exact match.** A method is accepted by (receiver type, method), each with its own differential test over empty, non-ASCII, supplementary-plane, boundary, and panicking inputs. A method that cannot be matched is rejected, not accepted with a documented difference: `f64::to_string` (Rust `1000000000000000000000`, JS `1e+21`) and `str::trim` (JS `trim()` also strips U+FEFF) are out.
- **Well-formed strings only.** Rust strings are UTF-8 and JS strings UTF-16. Every equivalence below relies on a string holding only whole scalar values, which a Rust `String` always does; a TS string with lone surrogates is outside the domain (§2). A `pub` function checks each parameter that may hold a string on entry (`Str.wellFormed`, which walks the value) and panics on one, so no later step meets it: a `String` / `&str`, or one anywhere in an open struct, an enum, an `Option`, a `Vec`, or a tuple. A private helper is not checked again; a closed type's strings came through its own `pub` functions, checked there; a type with no string is not walked. A string a TS callback returns is not checked (tested: lead, trail, and reversed halves, in an `Option`, a `Vec`, a nested struct, a variant and its field, a tuple, and a constructor, against pairs and U+10FFFF, `lone_surrogate.rs`).

### 6.1 Strings

The TS value is a plain `string`; operations that depend on the encoding go through the runtime `Str`, and reproduce UTF-8 byte units: `len` counts UTF-8 bytes, and `bytes` / `as_bytes` yield `u8`s.

What prints as the plain JS operation, and why that is the same:

- **Prefix, suffix, substring.** On well-formed strings a match on char boundaries is the same in UTF-8 bytes and UTF-16 units, so `is_empty`, `starts_with`, `ends_with`, `contains` need no encoding step. `char` and closure needles are rejected (tested: every pairing of 14 strings from empty to U+10FFFF).
- **Equality and literal patterns.** Well-formed strings are equal as UTF-8 exactly when they are as UTF-16, so `==` and string literal patterns print as `===`; `String::as_str` prints as the string itself (tested: 16 strings including the literals, a shared prefix, NFC vs NFD, U+FFFF, and a supplementary-plane neighbor).
- **`for c in s.chars()`.** A JS string iterates by code point, which for well-formed strings is Rust's sequence of scalar values, so it prints as `for (const c of s)` (tested: 14 strings across every UTF-8 length, the surrogate gap and U+E000, with `?`, early `return`, nesting, closures, and overflow in the body). `chars()` as a value and its adaptors are rejected.
- **`for t in s.split(c)`** with a `char` separator prints as `s.split(c)`. One code point occurs at the same places of a well-formed string in UTF-8 and UTF-16 (a supplementary one is a surrogate pair that appears nowhere else), and JS `split` keeps the empty pieces Rust keeps: leading, trailing, and between adjacent separators (tested: ten strings against separators of every UTF-8 length). A `&str` separator goes through `Str.splitStr` unless it is a non-empty literal, since an empty one splits differently (`"ab".split("")` is `["", "a", "b", ""]` in Rust, `["a", "b"]` in JS); the literal `""` is refused (§7.21). `split` as a value stays off the list, except before a consumer or `collect` (§7.12).
- **`split_once`** with a `char` or a `&str` prints as `Str.splitOnce`, `Option<(&str, &str)>`. `indexOf` finds the first match, and the two slices are the same strings on a well-formed input, including an empty needle (`"ab".split_once("")` is `Some(("", "ab"))` on both sides). A needle that is not text is refused.
- **ASCII case and trimming.** `to_ascii_lowercase` / `to_ascii_uppercase` fold `A`..=`Z` (`a`..=`z`) and nothing else, where JS `toLowerCase` folds all of Unicode. `trim`, `trim_start`, and `trim_end` remove `char::is_whitespace`, Unicode White_Space, by an explicit class: JS `trim` differs on U+0085 (Rust trims it) and U+FEFF (JS trims it). `trim_matches` and the one-sided forms take a `char` or a closure on one, matched per code point, and the one-sided forms a `&str`, stripped whole as often as it leads (an empty one strips nothing).
- **`find`** gives the UTF-8 byte offset of the first match: `indexOf` for a `char` or `&str` (UTF-16 units, converted by the UTF-8 length of what precedes), a code-point walk for a closure. `split` with a closure splits at each `char` it takes, empty pieces kept (`Str.splitBy`). Tested with every whitespace the two disagree on, empty patterns, and offsets past characters of every width (`str_more_equivalence.rs`).
- **`eq_ignore_ascii_case`** with a `&str` prints as `Str.eqIgnoreAsciiCase`: equal lengths, and each UTF-16 unit equal once `A`..=`Z` are folded to lower case. Rust folds the same letters on UTF-8 bytes and leaves every other byte; folding maps ASCII to ASCII and nothing else, so two strings agree folded as bytes exactly when they agree folded as units. No Unicode case folding on either side (`"é".eq_ignore_ascii_case("É")` is `false`). Tested on 20 strings pairwise, `@` and `` ` `` beside the letters among them.

What goes through the runtime, and what it keeps:

- **Slicing** `&s[a..b]`, `&s[a..]`, `&s[..b]` goes through `Str.slice`, which takes UTF-8 byte positions. It panics as Rust does and in Rust's order: a start past the end, an end past the end, a reversed range, then a start or end inside a character. That last message shows the character as `Debug` does, escaping a grapheme extender or a code point of category Zs (but space), Zl, Zp, Cc, Cf, Cs, Co, or Cn as `\u{..}`; the runtime tests these with the engine's Unicode properties, which agree with Rust's tables where both use one Unicode version (§3). `&xs[a..b]` on a `Vec` or slice checks the same order with Rust's slice messages (tested: seven strings covering every UTF-8 width and each escaped category, every start and end up to one past the length, nested slices, `as_bytes()`, and `Vec`s).
- **`strip_prefix` / `strip_suffix`** with a `&str` return `Option<&str>`. A prefix or suffix of a well-formed string on char boundaries has the same extent in UTF-8 and UTF-16, so the rest is the same string.

- **Ordering** `<`, `<=`, `>`, `>=`, and `cmp` compare code points, which is Rust's order of UTF-8 bytes. JS `<` compares UTF-16 units and so orders U+E000–U+FFFF above the supplementary planes, which Rust orders last; the runtime's `Str.cmp` moves those units back below the surrogates at the first unit that differs, and a shorter prefix orders first (tested: all pairs of 33 strings across every UTF-8 width, U+FFFF and U+E000 against U+10000, shared prefixes, NFC vs NFD, `String` against `&str`; replacing the key with plain UTF-16 order fails the test).

### 6.2 `char`

- **Representation.** A branded one-code-point `string` (`Char`). The brand also excludes lone surrogates, as a Rust `char` is a Unicode scalar value. JSON matches serde: a string of exactly one scalar value, anything else a schema failure.
- **Ordering.** Comparisons and range patterns use `Char.code` (`codePointAt(0)`), never the strings, for the UTF-16 order given above.
- **Conversions** are std's `From` only; `char::from_u32(n)` is `None` for a surrogate or past U+10FFFF, and `as` stays rejected.
- **Methods** are the ASCII and code-point ones, which need no Unicode table; `to_digit` and `is_digit` panic outside radix 2..=36 with Rust's message. The table-driven ones (`is_alphabetic`, `is_whitespace`, …) and `to_uppercase` (an iterator) are rejected; see §6.5.

Tested on 40 characters across every UTF-8 length boundary and the surrogate gap, all pairs for ordering, radixes 0–37, every `u8`, and `from_u32` around the gap.

### 6.3 `uuid::Uuid`

Added for the Oxide `Name` rule, which had to spell `Uuid::parse_str` by hand ([91 §4](./91-real-use-candidates.md#4-what-the-measurement-asked-of-purecrate-ts)). Verified against `uuid` 1.26.1.

- **Representation.** A branded `string` that only ever holds the lowercase hyphenated form (8-4-4-4-12), the one serde writes. In that form `===` is Rust's `==`, and JS string order is the order of the 16 bytes, since the hyphens sit at the same places in every value, so `==` and `<` print as themselves.
- **Parsing.** `parse_str` and `try_parse` accept what the crate's parser does, chosen by UTF-8 length as it chooses: 32 hex digits, hyphenated (36), braced (38), and `urn:uuid:` (45, the prefix in lowercase only), hex in either case; the result is the canonical form. The TS parser measures UTF-16 units, but a non-ASCII character fails the hex check at either length, so the accepted sets are equal. `uuid::Error` is opaque: nothing translated can read or compare it.
- **Rejected.** Generating (`new_v4`) and byte access. `to_string` is the value itself, the canonical form `format!("{u}")` prints (§7.21). `nil()` is the only constructor besides parsing.
- **JSON** is serde's: read from any string `parse_str` accepts, written canonical.

Tested on about 3,400 strings (every form the crate prints in three cases, each with one-character edits, cuts, extensions, and wrappings, and non-ASCII characters at the length boundaries) and all pairs of 45 UUIDs for ordering.

### 6.4 `usize`

A `number` checked to 0..2^53−1; the gap above that is in §3.

### 6.5 Other methods

- **`Vec` and slices**: `len`, and `is_empty` as `.length === 0`, on values, borrows, fields, slices, and `as_bytes()` results.
- **`Option::is_some` / `is_none`** print as `!== null` / `=== null`. This holds because `Option<T>` is `T | null` with nested `Option` rejected, so a falsy payload (`0`, `0n`, `false`, `""`) is still `Some`.
- **Unicode-table methods.** `str::to_lowercase` / `to_uppercase` are accepted (§7.21), with the version gap of §3; `ß` → `SS` and final sigma were measured to match. The others (`char::to_uppercase`, `is_alphabetic`, …) are not.

### 6.6 `std::cmp::Ordering`

- **Naming.** `Ordering` after `use std::cmp::Ordering;` (or `core::`, alone or in a group), or the full path `std::cmp::Ordering` in types, expressions, and patterns. `cmp::Ordering` through `use std::cmp;`, a renaming `use`, a glob, and importing the variants bare are refused, as is a crate item named `Ordering` beside std's. A crate that defines its own `Ordering` and does not name std's is unaffected.
- **Representation.** A fieldless enum `Ordering { Less, Equal, Greater }` with discriminants −1, 0, 1, added to the crate when it names std's (exported) or only calls `cmp` (internal). It prints like any crate enum, so `match`, tuple `match`, guards, `matches!`, and exhaustiveness need nothing new; rustc still checks the source against std's type.
- **`cmp`** on integers, `char`, `bool` (`false` first), `String` / `&str`, and `Uuid`, and the methods of `Ordering`, are rewritten (§7.10). `==` and `!=` on two `Ordering`s compare the variant: std derives `PartialEq`, so equality is structural, unlike a crate enum's (§5.1).
- **Refused.** `cmp` on floats (`partial_cmp` too), and on a crate type, `Option`, `Vec`, or tuple without an order (a crate type's `cmp`, derived or `impl Ord`'s, and the comparators composed for `Option`, `Vec`, and tuples are §7.25's); an `impl PartialOrd` other than `Some(self.cmp(other))`; `<` on `Ordering` or `bool`; `Ordering` in a struct or enum that derives `Serialize` or `Deserialize`, since serde gives it neither ([04 §3.2](./04-wire.md#32-serde-in-the-input)).

### 6.7 `str::parse` into an integer

`s.parse::<T>()`, `T` any integer type, is Rust's `T::from_str_radix(s, 10)`: an optional `+`, or a `-` when `T` is signed, then one or more ASCII digits, with the value in `T`'s range. Everything else is `Err`: an empty string, a sign alone, whitespace, `_`, a non-ASCII digit, a value out of range. Leading zeros are accepted. The target is named by the turbofish or by a `let` of `Result<T, ParseIntError>`. `Int.<t>.parse` checks the same grammar with an ASCII regular expression and the range on a `bigint`.

`ParseIntError` carries nothing: nothing translated reads its `kind()`, and the two sides agree on whether the result is `Ok` and on its value, not on which kind an `Err` is. A `usize` above 2^53−1 parses in Rust and panics in TS, as any `usize` that large does (§3). Floats, `bool`, `char`, and a crate's own `FromStr` are refused.

Tested with every integer type at its bounds and one past them, signs alone and doubled, leading zeros, whitespace, `_`, hex and exponent forms, and Arabic-Indic digits, through `ok()`, `match`, `map_err`, and `map_err(..)?`.

### 6.8 `format!`

`format!` prints integers of every width, `bool`, `char`, `String`, `&str`, and `Uuid` (and a crate type through its translated `Display`, §7.25), whose `Display` is the same text on both sides: an integer's decimal digits with a `-` (a `bigint` prints without its `n`), `true` / `false`, the characters themselves, and a `Uuid`'s canonical form, which is the only form its TS brand holds (§6.3). It prints as a template literal (`` `INV-${n}` ``); the text between arguments is escaped as a string literal is, and `` ` `` and `${` as a template reads them. A literal argument placed without a spec (a string, `char`, integer, or `bool`) is part of that text, escaped the same way (`format!("{}{n}", "b")` prints `` `b${n}` ``), and a template left with no argument is a string literal; a string, `char`, or `Uuid` placed alone is that value (`format!("{}", s)` prints `s`), and so is a value padded alone (`Str.pad(s, 5, "^")`); a `format!` (or an integer's `to_string()`) placed in another without a spec is its pieces in that place (`` `<${n}-${s}>` ``, not `` `<${`${n}-${s}`}>` ``), as the type-aware lint wants (`no-unnecessary-template-expression`). A literal runs nothing, and a spliced template runs its arguments where it ran them, so the order of what runs is unchanged.

- **Specs.** `{}`; a width (`{:5}`), with an alignment (`<`, `^`, `>`) and a fill (`{:*^5}`); and zero padding on an integer (`{:05}`). The width counts `char`s, as Rust's padding does, where JS `padStart` counts UTF-16 units, so a padded value goes through `Str.pad`, which counts code points; centered, the odd unit of fill goes right, as in Rust. Without an alignment an integer is right-aligned and the rest left. Zero padding goes after the sign (`-0042`) and overrides the alignment and the fill, as Rust's does (`Str.padZero`). Rust pads a `char`, a string, or a `bool` under `{:05}` with spaces and ignores a width on a `Uuid` (its `Display` writes the text directly), so both are refused rather than matched.
- **Refused.** Floats (`Display` of a float differs from JS past 1e21 and below 1e-7), `{:?}`, every radix and exponent (`{:x}` of a negative signed value prints its two's complement in Rust), `+`, `#`, a precision, a width from an argument (`{:1$}`), and a crate type whose `Display` is not translated, or with a width (§7.25). `x.to_string()` is the same text as `format!("{}", x)`, and refused where it is (§7.21).
- **Order of evaluation.** Rust evaluates the arguments as written, then the names captured inline (`{x}`); a template literal runs its `${..}` in the order it places them. A local, a literal, a field of one, or a reference to one reads the same whenever it runs, and nothing in an argument can change it but a statement or an assignment (`{ t.push('x'); 1 }`), which is refused; every other argument must be placed once and in the order written, or `format!` is refused with a message to bind it with `let` first. A crate type's `fmt` runs after every argument in Rust, where the template places it in TS, so no argument but such a read may be placed after one (§7.25). `?` in an argument is lifted before the template, as everywhere.

Tested on every integer type at its bounds, each alignment with a fill of every UTF-8 width, zero padding of negative values, `char`s and strings outside the BMP and with combining marks, escapes, named, positional, and captured arguments, and the order of arguments that panic (`format_equivalence.rs`); and as a shape of the strings generator, with arguments that panic, widths, fills, and captures (`generated_strings_equivalence.rs`).

### 7.1 `Option` and `Result` methods

The receiver is bound once. An argument that is a value, `unwrap_or(d)`, `ok_or(e)`, `or(o)`, `map_or(d, f)`'s `d`, and `expect(m)`, is evaluated before the `match`, whether or not the option is `Some`, as Rust does; JS `??` would skip it, and a `d` that overflows would then not panic. An argument that is a function runs only on the side that calls it: `map(f)`, `and_then(f)`, `filter(p)`, `is_some_and(p)`, and `is_none_or(p)` on `Some`, `unwrap_or_else(f)`, `ok_or_else(f)`, and `or_else(f)` on `None`, `map_or_else(d, f)` each on its own. `filter(p)` keeps the value where `p` is true; `is_none_or(p)` is `true` on `None`. A result that would be `Option<Option<_>>` (`and_then` with a function returning one) is refused, as both `None`s are `null`. `o.map(f).unwrap_or(d)` is one `match o { Some(x) => f(x), None => d }` when `d` is a name or a literal: it has no effect and cannot panic, so whether it runs before `f` or only on `None` is not observable.

On a `Result`, `ok()` is `Some` of the `Ok` value or `None`, `err()` the same of the `Err` value; `map(f)`, `and_then(f)`, and `is_ok_and(p)` run their function only on `Ok`, `map_err(f)`, `or_else(f)`, `unwrap_or_else(f)`, and `is_err_and(p)` only on `Err`; `unwrap_or(d)` and `map_or(d, f)`'s `d` run on both. `is_ok()` and `is_err()` test the side. `f` is a closure of one parameter without `?` or `return`, a function name, or a one-field tuple variant (`PreId::Numeric`), as for `Option::map`. `r.map_err(f)?` is `match r { Ok(v) => v, Err(e) => return Err(f(e)) }`: the mapped `Result` is not built. A plain `r?` whose error type is not the function's is the same `match` with the `impl From` member in place of `f` (`Err(X.fromS(e))`, §7.25); without one the error types must match.

### 7.2 Match guards

A `match` with a guard goes through the decision tree of a tuple `match` (a single value as a tuple of one): each element is tested once on a path, and where an arm's pattern has matched, its guard is tested with the arm's bindings read from their places; if it is false, the `else` is the tree of the arms after it that can still match there.

- A guard runs only when its pattern matched, and the arms are tried in Rust's order.
- A guarded arm covers nothing, so `A if g => .., _ => ..` sends a failing `A` to `_`.
- Where two literal arms may overlap (a range and a literal inside it), the later one is tested again after the earlier guard fails.
- A `?` or `return` in a guard is refused.

Tested with a guard that overflows only where its pattern matched, `_` after a guarded arm, overlapping literal arms, `bool` elements, and a name read only by the guard. Two earlier printings were replaced by this one ([CHANGELOG 0.3.0](../CHANGELOG.md#rationale-guards-and-option)).

### 7.3 Scalar consumers

`all`, `any`, `position`, `count`, and `sum` on `s.chars()`, `s.bytes()`, `s.split(c)`, and `xs.iter()` call the runtime's `Iter.all`, `Iter.any`, `Iter.position`, `Iter.count`, and `Iter.sum`, which run the loop std's default methods run: the source is evaluated once, the closure is passed as an arrow function (a function name as itself; neither may use `?` or `return`, which would have to leave the enclosing function), and the loop stops where std's does (`all` at the first `false`, `any` and `position` at the first `true`), so a predicate that would overflow on a later item does not run on it.

- `position` counts items (chars, not bytes, on `chars()`).
- `sum` adds from zero left to right with the checked operator, so it panics on overflow where a debug build does; it is refused on floats, whose `Sum` starts from `-0.0`.
- `find(f)` is the first item `f` takes. `max()` and `min()` order by `cmp` (`Ord.cmp`, or `Ord.cmpStr` by code point on `char`s, strings, and `Uuid`s), `max_by_key(f)` / `min_by_key(f)` by each key's `cmp`, computed once per item in order, and `max_by(f)` / `min_by(f)` by the closure's `Ordering`; of equals, `max` keeps the last and `min` the first, as std folds them. Over `Option` items each is refused (`Option<Option<_>>`).
- `fold(init, f)` evaluates `init` once the source is made and before any item, then sets the accumulator to `f(acc, x)` for each item in order (`Iter.fold`). The accumulator's type is `init`'s; an unsuffixed number there with no type from the context is refused, as Rust infers its type from `f`.
- `for (i, x) in ...enumerate()` reads a `usize` counter into `i` and advances it at the top of each pass, so `continue` keeps it right.

Tested on strings of every width, early stops before an overflow, `sum` overflowing either way, and `continue` in an enumerated loop.

### 7.4 `bool` patterns

`true` and `false` are tried in order as an `if` chain, like integer literals; a `match` naming both needs no `_`, and its last arm becomes the `else`. In a tuple `match` they split like any literal column. Tested with both named, one and `_`, `false | true`, a three-element tuple `match` with a guard, and `matches!`.

### 7.5 Tuple patterns

In `let`, a closure parameter, or a `for` variable, a tuple pattern becomes `match value { (a, b) => rest }`, which Rust's irrefutable pattern is: the value is evaluated once (a tuple expression left to right, so the first overflow panics), then each element is bound. A `mut` element binds a fresh name that the body rebinds with `let mut`. Tested with `mut` and `_` elements, an annotation, overflow in either element, `&(a, b)` over `iter()`, and `break` / `continue` in the loop.

### 7.6 `vec![a, b]`

Prints as `[a, b]`, elements evaluated left to right as in Rust. The `Vec` it builds is never mutated (no `push`, `insert`, `remove`, or index assignment unless it is bound to a `let mut` local, which owns an array of its own: §7.14), so sharing the element values with the array is unobservable. The element type comes from context like any literal's; `vec![x; n]` is rejected. Tested with element types from the return type and a struct field, `vec![]`, nesting, `Option` elements, and the first of several overflows reported.

### 7.7 `const` and discriminants

- **`const`** is folded by `check` with rustc's const-evaluation rules (checked arithmetic, wrapped shifts with the amount checked), and the TS holds the value, not the computation. rustc rejects a const that overflows, so there is nothing to throw at run time, and module load order cannot matter.
- **A const in a pattern is refused**: Rust compares with its value, where the IR would bind a new name that matches anything.
- **Discriminants** of a fieldless enum (explicit, or one past the previous; the first `0`) are folded the same way, in the `#[repr]` type or `isize` (64 bits). `e as T` is accepted only when `T` holds every discriminant, so the cast never truncates or wraps; it prints as a table indexed by `kind` (a constant variant folds to the literal). `x as usize` from a `u8`, `u16`, or `u32` holds every value on every target and is how Rust writes the last (std has no `usize::from(u32)`); it is the widening `usize::from` would be, the same `number` under another brand. Between any other two integer types that std's `From` does not join, `x as T` keeps the value modulo 2^bits of `T`, read signed for a signed `T`, as Rust's `as` does: `Int.<t>.cast(x)`, which for a `number` target takes the low bits with `<<` and `>>` / `>>>` (exact on any integer below 2^53, as JS shifts first reduce modulo 2^32) and for a `bigint` source or target `BigInt.asIntN` / `asUintN`. Into `usize` the result is Rust's 64-bit one, so above 2^53−1 it panics, as every `usize` that large does (§3). A pair `From` joins is refused as `as` and written `T::from(x)`. Tested over all 54 pairs at each type's bounds and the powers of two around 8, 16, 32, 53, and 64 bits (`int_cast_equivalence.rs`).

### 7.8 `const` in a block

Not folded: it becomes an immutable, typed `let` at the top of its block, in declaration order, so it is visible from the whole block as an item is. The value is computed at run time rather than folded, which is the same value: rustc, which runs on the input, rejects a const whose evaluation overflows, so the computation cannot panic where Rust would have folded one. A local const in a pattern is refused like a crate one, and so is a `let` of its name (rustc reads that `let` as a pattern too). Tested with a use before the declaration, a crate const and a discriminant in the value, an unused and a float const, one named like a crate item, one inside a `match` arm, and overflow computed from one.

### 7.9 Integer methods

`x.min(y)`, `max`, `abs`, `pow`, and the `checked_*`, `saturating_*`, and `wrapping_*` forms are computed from the exact result in `bigint`:

| Form | Result |
| --- | --- |
| `checked_*` | the exact result, or `None` outside the type's range (and on a zero divisor, and on `MIN / -1`) |
| `saturating_*` | clamped to the range; `saturating_pow` of a negative base to an odd exponent saturates to `MIN`, as std does |
| `wrapping_*` | the low bits; `wrapping_pow` works modulo 2^bits |
| `abs`, `pow` | panic outside the range as a debug build does ("attempt to negate with overflow", "attempt to exponentiate with overflow", measured on 1.98.1) |

An exponent is a `u32`; a power is not formed when its magnitude is certainly past the range (a base of magnitude two or more to an exponent of the type's width or more). Tested at every type's edges, `(-2).pow(31)` and `i8` powers near 127 included.

### 7.10 `cmp` and `Ordering`'s methods

- **`a.cmp(&b)`** is a call to the runtime, the receiver then the argument as its arguments, so each is evaluated once and in Rust's order. `Ord.cmp(a, b)` on an integer or `bool` is `Less` if `a < b`, `Equal` if `a === b`, else `Greater`: JS `<` orders numbers and `bigint`s as Rust does, and `false` before `true`. `Ord.cmpStr(a, b)` on a `char`, a string, or a `Uuid` goes through `Str.cmp`, by code point; a `char` is a string of one code point, and a `Uuid` its canonical form.
- **`is_eq` … `is_ge` and `reverse`** are a three-arm `match` on the receiver.
- **`then(o)`** is `Ord.then(receiver, o)`: both are evaluated, the receiver first, then `o` is picked on `Equal`. `o` runs, and can overflow, whatever the receiver is, as Rust evaluates a call's arguments.
- **`then_with(f)`** puts `f`'s body (a closure without parameters, `?`, or `return`) or the call `f()` (a function name) in the `Equal` arm, so it runs only there.

Tested with an overflowing `then` argument after a non-`Equal` receiver, an overflowing `then_with` body that must not run, a function name, a SemVer-style chain, `Ordering` in a tuple `match` with guards, `matches!` with the qualified path, and every predicate.

### 7.11 `impl Display` with a fixed text

`impl Display for X` whose `fmt` writes a text fixed per value becomes the method `X.toString(self): string` (`to_string` before `check::rename` spells it for TS), and `x.to_string()` in the crate calls it. The shapes taken: `f.write_str(t)` or `write!(f, "..")` (no `{}`; `{{` and `}}` read as braces), a `match self` whose arms are those or string literals, and `let t = <such a match>; f.write_str(t)`. The text is what `to_string()` gives in Rust: `write!` writes its literal with the braces unescaped, `write_str` its argument. A `fmt` with formatting arguments or several writes is §7.25's general case; this one prints as before, the literal or a `switch` returning one. Tested with each shape, a non-ASCII text, escaped braces, and a struct.

### 7.12 A list collected from text

`s.split(c).collect()` and `s.split(c).map(f).collect()` build a `Vec` whose length is the input's. `c` is a `char`, so the pieces are the ones `for t in s.split(c)` already walks, empty ones included; a `&str` separator, `split_whitespace()`, and `lines()` collect the same way (§7.21). `f` is a closure of one `&str` parameter, or a function name, with no `?` or `return`. The target is named by `collect::<Vec<T>>()`, `collect::<Result<Vec<T>, E>>()`, a typed `let`, or the function's return type.

Into a `Vec<T>`, the pieces (or `f`'s results) are the array. Into a `Result<Vec<T>, E>`, `f` returns `Result<T, E>` and `Iter.tryCollect` runs `f` in order and returns the first `Err`, which is what `FromIterator` for `Result` does, so a later piece is not evaluated. The literal separator `""` (§7.21) and a missing target type are refused; collecting other sequences is §7.13.

Tested with empty pieces, a non-ASCII separator, a function name and a closure, a turbofish and a typed `let`, an empty needle to `split_once`, and a `"boom"` after `"bad"` that panics only when the `Err` does not come first.

### 7.13 `map` and `filter` over a sequence

<!-- constrained-by ./02-authoring.md#31-state-is-a-value-sequences-are-rebuilt -->

`xs.iter()` (or `into_iter()`, `chars()`, `bytes()`, `s.split(c)`) through any `.map(f)` and `.filter(p)`, then a consumer (`collect`, `sum`, `fold`, `count`, `all`, `any`, `position`), or a `for`. Right after the source, before any stage, `.rev()` is a new array of the items reversed (`Slice.rev`), and `.zip(b)`, `b` another source or a `Vec`, a new array of pairs as long as the shorter (`Slice.zip`). Neither runs code of the crate, so making the array whole first is not observable; a stage before them (`map(f).rev()`, where Rust runs `f` from the back) is refused. Rust's adaptors are lazy: for each item, every stage runs, then the consumer, before the next item. `Iter.map` and `Iter.filter` are generators, so the TS runs in that order too, and a panic in a stage or in `sum`'s addition comes at the same item as in Rust. One stage before `collect` prints as the array method (`xs.map(f)`, `xs.filter(p)`): with nothing else running between the calls, the order of `f`'s calls is the same. `filter`'s predicate takes `&T`; it reads the item, as everything here does.

### 7.14 Growing and editing a `Vec`

`let mut v: Vec<T>` is the one array the output writes, by `v.sort()`, `v.sort_by(f)`, or `v.sort_by_key(f)` (`Slice.sortBy` / `Slice.sortByKey`: JS `sort`, stable since ES2019 as Rust's `sort` is, so equal elements keep their order; `sort_unstable` stays refused, as the order of equals may differ), by `v.push(x)` or `v.insert(i, x)` (`Slice.insert`: Rust's panic for `i` past the length, then `splice`, the same shift of the tail Rust makes), `v.remove(i)` (`Slice.remove`: Rust's panic for `i` at or past the length, then `splice`), or `v[i] = x` (`Slice.set`: Rust's panic at or past the length, where JS would grow the array, then the write). Rust evaluates an assignment's value before its place, and in `v[i] op= x` on a primitive the `x` before `v[i]`; `Slice.set(v, i, x)` reads `i` first, so where both `x` and something JS reads before it may panic, `x` is bound in a `const` first (`vec_edit_equivalence.rs` has a case of each). It is bound to an array of its own: `Vec::new()`, `vec![..]`, `.clone()`, and `.collect()` make one; any other value is copied when bound or assigned (`[...xs]`), because a TS caller may still hold the array a parameter, a field, or a returned value is. No closure captures it, and nothing pushes to a field, an element, or a parameter. So every other array is never written after it is made, and sharing one is unobservable, as before: `clone` of a `Vec` copies its elements (`[...xs]`, shallow, since the elements are not written either), and `clone` of anything else is the value.

### 7.15 Building a `String`

`String::new()` is `""`. `s.push(c)` and `s.push_str(t)` on a local `let mut s: String` are written by `check` as the assignment `s = s + c`, so every later pass sees an ordinary write of `s` (narrowing forgets what it knew, a loop's head joins it); nothing pushes to a field, an element, or a parameter. JS strings are values, so `+` makes a new one and no other holder of the old string sees a change, as no other holder of a Rust `String` does. Both languages concatenate by code point: UTF-8 bytes and UTF-16 units of the parts in order are those of the whole. A push prints as `s += c` where the piece needs no statements. `collect::<String>()` over a sequence of `char`s collects them as a `Vec<char>` and joins it (`.join("")`); nothing else collects into a `String`. Tested with empty, ASCII, two- to four-byte, and surrogate-edge text, separators of every UTF-8 length, and the length of what was built (`string_build_equivalence.rs`).

### 7.16 Control flow on patterns and ranges

- **`loop`** is `while true`, printed `for (;;)`. Its type is `!` when no `break` leaves it, `()` when its `break`s carry nothing, and otherwise the one type every `break v` carries. `break v` puts `v` where the loop's value goes: into the variable a `let x = loop { .. }` declares without a value, as the `return` of a loop that ends the function, or run for its effects where the value is unread. No path leaves the loop except a `break`, so the variable is assigned before it is read, which TS checks.
- **`while let P = e { body }`** is `loop { match e { P => body, _ => break } }`: `e` is evaluated before every pass, as Rust's desugaring does, and `continue` evaluates it again.
- **`if let P = e { a } else { b }`** is `match e { P => a, <every other value> => b }`; **`let P = e else { d };`** is `match e { P => <the rest of the block>, <every other value> => d }`, so `P`'s names are bound for the rest and not in `d`, which rustc checks leaves (`return`, `break`, `continue`, a panic). Where `P` is `Some(x)`, `Ok(x)`, or `Err(x)`, it is `let x = match e { .. }`. `P` is any pattern a `match` arm may be that can fail to match; a struct pattern, a type annotation, and a pattern that always matches are refused.
- **`for i in a..=b`** tests `i <= end`. Rust's `RangeInclusive` stops at `b` without computing `b + 1`, so `u8`'s `0..=255` does not overflow; the TS steps `i` past `b` once, as a JS number or `bigint` the body never sees, so it cannot wrap either. `a > b` runs no pass.
- **`for i in (a..b).rev()`** starts at `b - 1` and steps down while `i >= a`; `(a..=b).rev()` starts at `b`. `a` and `b` are evaluated once, `a` first, as Rust builds the range before calling `rev`. The value below `a` that ends the loop (`-1` for an unsigned `0`) is never seen by the body. `rev` on a sequence is §7.13's.
- **`t.N`** reads a tuple's element `N`, as `t[N]`; an index past the tuple is refused.

Tested with `break` values from the arms of a `match` (a `switch` in TS) and from nested loops, a loop left only by `return`, `while let` on a method, a `Result`, and a variant inside `Some`, `..=` and `.rev()` at both ends of `u8`, `i8`, and `u64` (past 2^53), empty ranges, bounds that panic in Rust's order, and `let`-`else` with several names, `mut`, `continue`, and `break` (`loop_value_equivalence.rs`, `if_let_equivalence.rs`), and as statements of the statements generator.

### 7.17 Panics

Each of these panics in Rust, so it throws in TS (`Panic.raise(m)`, a `Panic` as overflow's), with the message Rust's payload holds, which `purecrate-ts test` compares:

- **`panic!()`** is `explicit panic`; **`panic!("..", args)`** the text `format!` makes of the same arguments (§6.8, its rules and refusals).
- **`unreachable!()`** is `internal error: entered unreachable code`; with a message, that, `: `, and the message.
- **`assert!(c, "..", args)`** is `if !c { panic!("..", args) }`: the message is built only when `c` is false, as Rust builds it. **`assert!(c)`** panics with `assertion failed: ` and `c` as rustc prints it, which is reproduced for names, literals as written, unary and binary operators, casts to a named type, calls, method calls, fields, indexing, references, and parentheses; any other condition is refused and asks for a message.
- **`o.unwrap()`** on `None` is ``called `Option::unwrap()` on a `None` value``; **`o.expect(m)`** is `m`, evaluated before the `match`, on `Some` too.

Refused: `Result::unwrap` / `expect` / `unwrap_err` / `expect_err`, `assert_eq!`, and `assert_ne!`, whose messages print a value with `{:?}`, which the output does not reproduce (§6.8); `todo!` and `unimplemented!`. A panic has type `!`. Neither TS nor the generator's flow analysis narrows past one: `Panic.raise` is a property with no written type, which TS does not read as ending control flow, so what each knows after a panic agrees. Statements after a panic in the same block are not printed.

Tested with every message form, a message whose argument overflows only when the assertion fails, conditions of each shape, a panic in a `match` arm, an `if` side, and a loop, and `expect` with a literal, a parameter, and a `format!` (`panics_equivalence.rs`); and as statements and `unwrap` / `expect` of the statements generator.

### 7.18 Reading a `Vec`: `get`, `first`, `last`, `contains`

`xs.get(i)` is the element or `None` at or past the end (`Slice.get`), `xs.first()` is `get(0)`, and `xs.last()` the last element or `None` when empty (`Slice.last`); on a `Vec<Option<T>>` each is refused (`Option<Option<_>>`). A `get` with a range is refused. `xs.contains(&x)` compares each element with `x` as the derived `eq` does (`Slice.contains`, through `Eq.deep`): NaN is not equal to itself and `-0.0` equals `0.0`, as in Rust, where JS `includes` would find NaN. Tested on empty and one-element lists, `usize::MAX` as an index, floats with NaN and `-0.0`, strings, and structs (`std_more_equivalence.rs`).

### 7.19 `BTreeMap<String, V>` and `BTreeSet<String>`

A map is a TS `Map<string, V>` (`ReadonlyMap` but for a local it writes), a set a `Set<string>`. A JS `Map` iterates in insertion order and a caller's may have been filled in any, so every read in order sorts the keys first (`BTree.keys`, `entries`, `values`): by code point, as Rust orders a `String`'s UTF-8 bytes, where JS's `sort()` compares UTF-16 units and puts U+E000..U+FFFF above a key outside the BMP. `for (k, v) in &m`, `m.iter()`, `m.keys()`, `m.values()`, and a set's `iter()` give that array, into a `for`, a consumer, or `collect`.

- `get(k)` is the value or `None` (`BTree.get`: `Map.get` gives `undefined`); `contains_key(k)` / `contains(k)` is `has`; `len()` the `size`. A key argument is a `&str` or a `String`.
- `insert(k, v)` gives the replaced value or `None`, a set's `insert(k)` whether `k` was new; `remove(k)` the removed value or `None` (on a set, whether it was there). Each writes only a `let mut` local bound to a map or set of its own (`BTreeMap::new()`, `clone()`, `collect()`; any other value is copied when bound), which no closure reads, as §7.14's `Vec`.
- `collect()` from `(String, V)` pairs builds a map, a later key's value replacing an earlier one's, as Rust's `FromIterator` does; from `String`s a set.
- `==` compares keys and values as the derived `eq` does (`Eq.deep`, order aside: both sides hold each key once).
- Keys are `String` only. A map of `Option` or `()` values is refused: `get` of a missing key and of such a value would be the same. `HashMap` and `HashSet` are refused: Rust leaves their order unspecified. `cmp`, `entry`, `get_mut`, `range`, `first_key_value`, and indexing `m[k]` are refused.

A `pub` function checks a map's keys and values and a set's keys for lone surrogates on entry (§6). Tested with keys on both sides of U+FFFD and outside the BMP, maps built in reverse order, a key twice, `__proto__` and `constructor` as keys, the caller's map left as it was, overflow at the first value in key order, and derived `==` on a struct holding a map and a set (`btree_equivalence.rs`, `lone_surrogate.rs`); and as statements of the collections generator.

### 7.20 Type parameters

A struct, an enum, an inherent `impl` block, and a function may have type parameters (`struct Page<T>`, `impl<T: Clone> Page<T>`, `fn first<T: Clone>(xs: &[T]) -> Option<T>`), each a TS type parameter of the one emitted declaration: nothing is copied per type. A `T` is opaque in the body that has it. It may be moved, returned, put in a `Vec`, an `Option`, a tuple, a struct, or a variant, cloned (`clone` of a value nothing writes is the value, §7.14), and compared with `==` / `!=` (`Eq.deep`, which compares any value part by part as the derived `eq` does).

- **Bounds.** `Clone`, `Copy`, `PartialEq`, `Eq`, and `Debug`, structural, and a trait of the crate, `PartialOrd`, `Ord`, `Display`, and `Default`, which carry a dictionary (§7.25), on the parameter or in a `where` clause, by name or by path (`std::cmp::Ord`, `fmt::Display`); any other bound, a const parameter, and a default are refused. A `T: Ord` (or `PartialOrd`) is ordered through its dictionary's `cmp`: `<` .. `>=`, `cmp`, `max`, `min`, `sort`, and the iterator's `max` / `min` on a `T`, and on an `Option`, a `Vec`, or a tuple of one; `clamp` on a `T` alone is refused, as std's panic message where its bounds cross depends on `T`'s type (an integer's and a `char`'s name the bounds). On a struct's or an enum's own parameters the std bounds stay inert, as in 0.20.0. `Debug` is inert (`{:?}` is refused anyway).
- **Inference.** At a call, each type argument comes from the arguments (first-order: `Vec<T>` against `Vec<u32>` gives `u32`), else from the type the call's value goes to; at a construction (`Page { items, total }`, or a generic newtype's `Wrap(x)`), from the fields or the type the value goes to; a method of `impl<T> Page<T>` takes the receiver's. One that nothing gives is refused and asks for an annotation. A turbofish on a call (`empty::<u32>()`) is refused with the same advice.
- **Instantiations refused.** A type argument that is an `Option`, `()`, or `!` (a generic item's `Option<T>` or map value would print as `null` / `undefined` both ways, as §6's `Option<Option<_>>`), and one `Eq.deep` does not compare as Rust does (`ParseIntError`, `uuid::Error`, a function). A generic newtype written with one in a type (`Wrap<Option<u32>>`) is refused too, as `struct W(Option<u32>)` is: the brand on `T` would drop `null`.
- **Output.** A constructor (`of`, a variant) that holds no value of some parameter gives the type with `never` there (`Tree.Leaf(): Tree<never>`), which any instantiation takes, as the type's fields are read only. A generic newtype is its content branded, generic as any type: `export type Wrap<T> = T & { readonly "c.Wrap": true }`, `of: <T>(value: T): Wrap<T>`; a closed generic type's `unsafeMake` constructor is generic the same way.
- **On the wire** (design/04 §3.3): a generic type's schema is a function of its parameters' schemas (`Page(User)`), its writer of their writers (`toJson.Page(x, writeT)`), and `fromJson.Page(text, wireT)` takes them too. A bound's dictionary is a parameter as a writer is: §7.25.

Tested with a generic struct as a parameter, a field, and a result, nested in `Option` and `Vec`, a two-parameter struct and enum, a recursive generic enum through `Box`, a generic function called at two types in one body and recursively, struct update on a generic struct, a generic newtype built, read through `.0`, and returned at two types, and `==` on generic values (`generics_equivalence.rs`); the refusals in `check`'s `generics.rs` and `newtype.rs`; on the wire, a struct holding a generic struct and a generic newtype, a two-parameter enum, and a recursive generic enum read from serde_json and written back byte for byte in each library (`wire_write.rs`). `purecrate-ts test` calls a generic function with every parameter at `i32`, which every bound listed above holds of; a parameter with a crate trait's bound at each type that implements it (§8.4).

### 7.21 Cutting and building text

<!-- constrained-by #3-known-non-equivalences -->

Accepted on a `String` or `&str`: `to_lowercase()` and `to_uppercase()`, `split(p)` with a `&str` or `String` separator, `split_whitespace()`, `lines()`, and `repeat(n)` (`n` a `usize`); `xs.join(sep)` on a `Vec` or slice of `String` or `&str`, `sep` a `&str` or `String`; and `x.to_string()` on an integer, `bool`, `char`, string, or `Uuid`. The pieces of `split`, `split_whitespace`, and `lines` stand where `split(c)` does: a `for`, a consumer, `collect`, and `map(f)` / `filter(p)` into them (§7.12, §7.13). Each makes its pieces into a new array at once, which runs no code of the crate, so Rust's laziness is not observable.

- **Case.** `to_lowercase` / `to_uppercase` print as JS `toLowerCase()` / `toUpperCase()`. Both apply Unicode's full case mappings (`SpecialCasing`, not the simple ones): `ß` → `SS`, `ﬁ` → `FI`, `İ` → `i̇`, and a final sigma by its context (`"ΟΔΟΣ"` → `"οδος"`), with no locale. Compared on every code point U+0000..=U+10FFFF and on those context cases, Rust 1.98.1 and Node 24.20.0 agree everywhere. The result depends on each side's Unicode version, so equivalence holds where the Rust toolchain and the JS engine carry the same one (§3).
- **`split` with a `&str`.** A non-empty well-formed separator matches at the same places in UTF-8 and UTF-16 (§6.1's argument for `contains`), and both languages take the leftmost match, then search after it, keeping empty pieces; so a non-empty literal prints as JS `split(", ")`. An empty separator differs: Rust splits at every char boundary with an empty piece at each end (`"ab".split("")` is `["", "a", "b", ""]`, `"".split("")` is `["", ""]`), JS at every UTF-16 unit with neither. A separator that is not a literal may be empty, so it goes through `Str.splitStr`, which takes JS `split` for a non-empty one and the code points between two empty pieces for an empty one. The literal `""` is refused, with `s.chars()` as the alternative.
- **`split_whitespace`** splits on runs of `char::is_whitespace` (Unicode White_Space) and drops the empty pieces. JS `\s` is a different set (it holds U+FEFF and lacks U+0085), so `Str.splitWhitespace` names Rust's 25 code points in its class, as `Str.trim` does (§6.1).
- **`lines`** splits after each `\n`, drops it and then one `\r` before it, and gives no line after a final `\n`: `"a\r\nb"` is `["a", "b"]`, `"a\rb"` stays one line, `"a\n\r"` is `["a", "\r"]`, `"\n"` is `[""]`, `""` is `[]`. `Str.lines` walks the `\n`s in the same order.
- **`join` and `repeat`** concatenate, by code point on both sides (§7.15): `xs.join(sep)` prints the separator always, as JS's default is `","`; `s.repeat(n)` is JS `repeat`. Neither has a separator or count that differs. Past what memory holds the two fail differently: Rust panics with `capacity overflow` where the byte length passes `usize::MAX` and otherwise builds 2^29 bytes and more (until the allocator aborts), while JS throws a `RangeError` past 2^29 − 24 UTF-16 units (Node 24.20.0); a count of 2^53 or more already panics in TS as a `usize` (§3). Not matched.
- **`to_string`** is `format!("{}", x)`, the same `Callee`, so the same text (§6.8): an integer's digits, `true` / `false`, the `char`, the `Uuid`'s canonical form. A string, a `char`, and a `Uuid` are already that text (a `Uuid`'s brand holds only the canonical form), so each prints as the value itself, as `clone` does. A float is refused, as by `format!`; the crate's own `impl Display` keeps its `toString` (§7.11).
- **Refused.** The literal separator `""`; `join` on items other than text, or with a `char` separator; `concat`, `splitn`, `rsplit`, `split_terminator`, `char_indices`, and `to_string` on a float.

Tested on texts with final sigma, `ß`, `İ`, ligatures, and letters outside the BMP; separators that are empty, repeated, overlapping, multi-byte, `\n`, and `\r\n`; every White_Space code point beside U+FEFF, U+180E, and U+200B; `\r` and `\n` in each order; `join` over empty lists and empty items; `repeat` 0, 1, and 3 times; and `to_string` at each integer type's bounds (`strings_more_equivalence.rs`); the refusals in `check`'s `strings_more.rs`; and as shapes of the strings generator, each in a `for`, a consumer, and `collect`, seeds 1 to 120.

### 7.22 Iterator adaptors and ranges

<!-- constrained-by #713-map-and-filter-over-a-sequence -->

§7.13's sequences take three more stages, two more sources, and ranges, each before a consumer, `collect`, or as a `for`'s source; a `for` now walks any of §7.13's sequences, its stages run as the loop asks for each item.

- **Stages.** `filter_map(f)`, `f` returning an `Option`, keeps each `Some`'s value (`Iter.filterMap`). `flatten()` over `Vec` items gives each one's elements in order (`Iter.flatten`), over `Option` items each `Some`'s value (`filter_map` of the item itself). `flat_map(f)` is `map(f)` then `flatten()`: `f` returns a `Vec` or an `Option`. Each is a generator, as `Iter.map` is, so `f` runs on an item when the consumer reaches it, after the previous item's whole chain, as Rust's lazy adaptors run: a panic in `f` comes at the same item, and `find` stops before an overflow a later item would cause.
- **`windows(n)` and `chunks(n)` on a `Vec` or slice** are sources: a new array of the slices (`Slice.windows`, `Slice.chunks`), each a `Vec` here, indexed as one (`w[0]`, `w.len()`). They run no code of the crate, so making the array first is not observable, as `rev` and `zip` (§7.13). `n` of 0 panics with Rust's message (`window size must be non-zero`, `chunk size must be non-zero`), literal or not, when the method is called: the receiver and `n` are evaluated first, in that order. A `chunks` slice past the end is shorter, as Rust's last one is.
- **Ranges.** `(a..b)` and `(a..=b)` with both ends, written as a method's receiver, are a sequence of one integer type (an unsuffixed start takes the end's, as in a `for`), `a` then `b` evaluated once. `Iter.range(a, b)` / `Iter.rangeInclusive(a, b)` hold it as an arithmetic sequence (first item, count, step) computed as it is walked, not an array, so a consumer that stops early stops the walk. `.rev()` on one is the same items from the last; `.step_by(k)` keeps the first item and every `k`th after it, `k` a `usize`, evaluated after the range, and 0 panics with `assertion failed: step != 0` when `step_by` is called, on an empty range too. Each makes a new sequence at once from the one before, so they compose in the order written: `(a..b).rev().step_by(k)` steps down from the last item (`b - 1`, `b - 1 - k`, …), while `(a..b).step_by(k).rev()` is the items of `(a..b).step_by(k)` last first, which end at `a` and start at the last item on `a`'s grid; `(0..10).rev().step_by(3)` is 9, 6, 3, 0 and `(0..10).step_by(3).rev()` is 9, 6, 3, 0 too, but `(0..9)` gives 8, 5, 2 and 6, 3, 0. rustc accepts `step_by(k).rev()` only where std's range is `ExactSizeIterator` (`a..b` up to 32 bits and `usize`, `a..=b` up to 16 bits), and the output takes what rustc takes. **No step overflows:** the items and the count are JS numbers (every item, and every distance between two, of a type up to 32 bits or a `usize` is below 2^53, so exact) or `bigint`s for 64 and 128 bits, and the value one step past the last item, which `step_by` and `..=` compute and Rust's never does, is never read, so `(250u8..=255).step_by(3)` is 250, 253, as Rust gives it. A range is not a value: `let r = (0..n);`, `r.contains(&x)`, a range's `rev()` bound by `let`, and `zip` with a range are refused. `step_by` on anything but a range (`xs.iter().step_by(2)`) is refused; index with a stepped range (`(0..xs.len()).step_by(2).map(|i| xs[i])`). A `for` over a plain range or its `rev()` stays §7.16's loop; with `step_by` it walks the range's sequence (`for (const i of Iter.range(0, n).stepBy(2))`).
- **`dedup()` and `dedup_by_key(f)`** write a local `let mut v: Vec<T>` as `sort` does (§7.14): each run of elements equal by `==` (or whose keys are), kept as its first (`Slice.dedup`, `Slice.dedupByKey`). Each element is compared with the last one kept, as std does, through `Eq.deep`, so NaN is not equal to itself (both stay) and `-0.0` equals `0.0` (the first stays). The key is computed for the element, then for the last kept one, in std's order. A type `==` does not compare as Rust does (`ParseIntError`, §5.1) is refused.
- **An unsuffixed integer bound by `let`** (`let mut s = 0;`) takes its type from the first later use that asks one of it, in the order the function is typed (source order): an operand of an arithmetic or comparison operator whose other side is typed (`s += i`, `s < n`), a call's parameter, a typed `let`, or the function's result (`s` at the end of a `u32` function). rustc infers the literal's type from all its uses and they must agree, so the first that fixes one is rustc's; to find it, the rest of the block is typed once and set aside, then typed again with the type found, so every use is checked against it as against a written annotation (`let mut s: u32 = 0;`), which is what the output prints. Where no use asks for a type (rustc's `i32` default), it stays refused. A shift amount, a cast's operand, and a method's receiver do not fix a type; nor does a `let` in the search for another's.

Refused, besides those above: `flat_map(f)` with `f` returning another iterator (`s.chars()`, or any `IntoIterator` but `Vec` and `Option`), `flatten` over other items, `filter_map` with `f` returning other than an `Option`, `windows` and `chunks` as values, open ranges (`(a..)`), ranges of `char`, and `skip`, `take`, and other adaptors.

### 7.23 Associated consts and paths through modules

<!-- derived-from #77-const-and-discriminants -->

- **An associated const** (`impl T { const N: u32 = 3; }`, on a struct, an enum, or a generic type) is folded as a crate const is (§7.7): its type is an integer, a float, `bool`, `char`, or `&str`, its value of literals, consts, discriminants, and operators, which may read another as `Self::N`. The TS holds the value as a member of `T`'s companion, `N: 3 as U32`, cast to the type where the literal is not already (`"x" as string`), since `as const` would give the member the literal's type. `Self::N` in the `impl` (inside a macro's tokens too, `assert!(n <= Self::N, ..)`) and `T::N` anywhere are `T.N`; a crate or local const may read one. rustc folds it before the program runs and rejects one that overflows, so the read cannot panic, and no module load order can show a value before it is set: a companion's methods run only after every file is loaded. A non-`pub` one is not on the companion, as a non-`pub` method is not (§4.1), but `tyN`, exported from `T`'s file and not from `index.ts`. On a generic type the value cannot depend on the parameter (its type is a scalar), so `Page::<u32>::SIZE` and `Self::SIZE` read the one member.
- **A path through the crate's modules** (`crate::m::f`, `self::m::f`, `super::f`, `super::super::m::T::N`, a child's `m::E::V`) names the item alone, as modules are flattened and names are unique across the crate (design/02 §3.3): it is resolution, nothing runs differently. The prefix is dropped before lowering, from code and from a macro's tokens (`matches!(e, crate::m::E::A)`), as `std::cmp::` is before `Ordering`; a segment after `::` or `.` is not dropped. Privacy is rustc's, which `check` runs on the crate as written: a call to an item another module keeps private is refused as rustc refuses it (`[rustc/E0603]`; `E0624` for an associated const or function).

Refused: an associated const in a pattern, as a crate const is (Rust compares with its value; write a guard), and one named like a companion member (a variant, `of`). A trait's const is a member of each implementing type's companion, read as `Item::N` there and `T::N` through a bound (§7.25).

Tested against Rust with associated consts of every type (a non-ASCII `&str` and `char`, a negative float, a `u64` past 2^53), a private one read through a method, one reading another and a crate const, a crate const and a local const reading one, one on a generic type, products and sums with them overflowing at the edges, and calls, constructions, `match` arms, and `matches!` through `self::`, `super::`, `super::super::`, and a child module (`paths_equivalence.rs`); `crate::` through `build` on a single file, and privacy as rustc's refusal (`build.rs`); the refusals in `check`'s `assoc_consts.rs`; and as a statement of the statements generator, which reads a seed's module of associated consts, functions, and an enum through `crate::`, `self::`, and the module, seeds 1 to 120.

### 7.24 Slice patterns

<!-- constrained-by #72-match-guards -->

A slice pattern matches a `&[T]`: a slice parameter, `xs.as_slice()` or `&xs[..]` of a `Vec`, `*xs` (whose elements then bind values, as for `Copy` items), or `o.as_deref()` of an `Option<Vec<T>>` inside `Some(..)`. `as_slice()` and `as_deref()` are the value, as every reference is (§7.14: nothing writes the array while the slice is borrowed). Accepted in a `match` arm, an element of a tuple arm, `if let`, `let`-`else`, `while let`, and `matches!`, with guards: `[]`, `[x]`, `[x, y]`, `[x, ..]`, `[.., x]`, `[x, .., y]`, `[x, rest @ ..]`, `[rest @ .., x]`, `[first, rest @ .., last]`, and any number of elements on either side of `..`. An element is any pattern a tuple's element may be (`_`, a name, a literal or range, a variant, `Some(..)`, a tuple, a struct pattern), nested as deep as the types are; a name binds the element (`&T` in Rust, the value here, as in `for x in &xs`). `[..]` is `_` and `[rest @ ..]` a name. `|` joins slice patterns that bind nothing.

The `match` goes through §7.2's decision tree, where a slice is one more kind of value to test. Its length is tested first, as rustc splits the lengths for exhaustiveness: with `m` the longest fixed length plus one, or the most elements a `..` pattern names before `..` plus the most after, if more, each length below `m` is a case of its own, and every length from `m` on is one last case, which only patterns with `..` take. In a case, each element a pattern names is a value tested further in, where it sits: `Slice.at(xs, i)` from the front and `Slice.at(xs, xs.length - k)` from the back. The case has fixed the length, so neither is out of range, and the `Slice.at` check (which panics past the end) never fires; it is kept so the output reads the same under `noUncheckedIndexedAccess`. Lengths whose cases run the same code share one test (`xs.length <= 1`), and the last test is the `else`. Rust's arms are tried in order and a guard runs only where its pattern matched, which the tree keeps (§7.2): a guard that overflows panics only on the lengths where Rust runs it.

`rest @ ..` binds `Slice.range(xs, front, xs.length - back)`: a new array of the elements between, where Rust's is a view into the same slice. The values are equal, and neither side writes them (a slice is read-only), so the copy is not observable; it costs `O(n)` where Rust's costs nothing, and a guard that reads `rest` copies again in its arm. A loop that walks `cur = rest` copies on every pass.

Exhaustiveness is checked twice. `check` covers the lengths as rustc does (`[] + [_, ..]` is exhaustive; `[] + [_]` misses `[_, _, ..]`; `[x, ..] + [.., y]` misses `[]`; a guarded arm covers nothing) and names what is missing. Within a length, the elements are covered by the tree: where a path of a slice `match` runs out of arms, the `match` is refused and asks for a last `_`. That is conservative where the elements are covered only by ranges spanning their whole type (`[0..=255]` on a `&[u8]`), which rustc accepts. rustc runs on the input too.

Refused: `ref` or `mut` on `rest @ ..`, two `..` in one pattern, `|` of slice patterns that bind names, and a slice pattern on anything but a slice; `.to_vec()` stays off the allow-list (an owned copy of a rest is `rest.iter().copied().collect()`, or `cloned()`). Tested with every length from empty to past the longest pattern, `u32::MAX` sums that overflow only in the arm that runs, guards that overflow only where their length matched, a guard that reads `rest`, literal, `char` (non-ASCII and outside the BMP), `&str`, variant, `Option`, tuple, and struct elements, a tuple of two slices, slice patterns inside one on a `&[&[u32]]`, `Some` of a slice, `if let`, `let`-`else` with `mut`, `matches!` with `|` and a guard, `while let` and a `loop` walking `cur = rest` (`slice_patterns_equivalence.rs`); the refusals in `check`'s `slice_patterns.rs`; and as `match *xs`, `if let [p, rest @ ..]` / `[rest @ .., p]`, and `matches!(*xs, ..)` in the patterns generator.

### 7.25 Traits

Accepted from 0.22.0 (decided 2026-10-15: every part below, `Default` and `From` included, and the change to 0.20.0's output).

A trait is a record of functions over a type, and a type's companion is already one: `export const Item = { of, price: (self: Item): I64 => .. }`. A trait therefore prints as the type of a record, an `impl` as members of the implementing type's companion, and a bound `T: Tr` as one more parameter carrying the record for `T` (a dictionary). Nothing is looked up at run time: a value carries no tag that names its type (a struct is a plain object), so every call is resolved where the types are known, as a generic type's wire schema is (§7.20).

- **Trait definitions.** `trait Tr { .. }` with methods taking `&self` or `self`, functions without a receiver (`fn zero() -> Self`), default bodies, and associated consts, with a default or without. It prints in its own file as `export type Tr<Self> = Readonly<{ RATE: I64; price: (self: Self) => I64; zero: () => Self; .. }>`, `Self` its one type parameter, a member per const and method (camelCase, as a method is); its default bodies print in the companion `export const Tr = { total: <Self>(dict: Tr<Self>, self: Self): I64 => .. }`, where a call to another of the trait's methods (`self.price()`, `Self::zero()`) and a read of its const (`Self::RATE`) go through `dict`. A trait without default bodies has the companion `{}`. A supertrait (`trait Tr: Base`) makes the type `Base<Self> & Readonly<{ .. }>`, so one dictionary serves both bounds; a trait of supertraits alone (`trait Both: A + B {}`) is their intersection. Refused: associated types, type parameters on the trait (`trait Conv<T>`) or on its methods, a `where` clause on either (`where Self: ..`), `&mut self` and a typed receiver (`self: Box<Self>`), as everywhere ([07 §6](./07-roadmap.md#6-not-doing)); a supertrait that is not a trait of the crate (`trait Tr: Clone`); a trait with no method, const, or supertrait, whose dictionary would hold nothing; and an `unsafe` or `auto` trait, and an `unsafe`, `async`, or `extern` method.
- **Implementations.** `impl Tr for X` where `X` is a struct or enum of the crate, with or without type parameters, as long as its own parameters carry only §7.20's bounds (`impl<U: Clone> Tr for Bag<U>`). Each method becomes a member of `X`'s companion, as an inherent method is, and each const a member holding its folded value (§7.23), the trait's default where the `impl` writes none; all are public, as the trait's members are, whatever the trait's own visibility. A default the `impl` does not override becomes `total: (self: X): I64 => Tr.total(X, self)`, after the companion's other members. That member refers to `X` inside `X`'s own initializer, which is safe only because the call is deferred and every member has an explicit return type (TS7022 otherwise): the output already gives every member one, and this makes it an invariant. On a generic `X`, a member takes the `impl`'s type parameters it names, `never` for one named only in its result (`zero: (): Bag<never>`, which any `Bag<T>` takes) and none for one it does not name. Refused: an `impl` on a type outside the crate (`impl Tr for u32`, `impl Tr for Vec<X>`: there is no companion to put it in), a blanket `impl<T: Base> Tr for T`, an `impl` whose own parameters need a user trait (`impl<T: Tr> Tr for Page<T>`, whose dictionary would be a function of `T`'s, as a generic wire schema is; the path is there when a use asks), a negative `impl !Tr for X`, and any name the companion already holds: a trait method or const named like an inherent method or const, a variant, `of`, a member a std trait gives (`cmp` of `Ord` or `PartialOrd`, derived or written, `default`, `toString` of `Display`, `tryFrom`, an `impl From`'s `fromS`), or another trait's member on the same type. Rust resolves those by its own rules; the output has one namespace, so they are refused rather than emulated.
- **Calls on a known type.** `i.price()`, `Item::price(&i)`, and `Priced::price(&i)`, where `i: Item`, all print `Item.price(i)`, exactly the call an inherent method gets, a default the `impl` does not write included (`Item.total(i)`); a function without a receiver is called by the type (`Item::zero()`), or as `Priced::zero()` where the value goes to an `Item`, and a const is `Item.RATE`. `<Item as Priced>::price(&i)` is refused: it is only needed where the companion's namespace already refuses.
- **Calls through a bound.** A function or method with `T: Tr` takes one dictionary per (parameter, bound that carries one), after its other parameters, in the order the parameters and bounds are written: each parameter's bounds as written, on the parameter and then in `where`, and an inherent `impl`'s parameters before the method's own. `fn total<T: Priced>(xs: &[T]) -> i64` prints `<T>(xs: ReadonlyArray<T>, pricedT: Priced<T>): I64`, and `x.price()` in it prints `pricedT.price(x)`; `T::zero()`, `T::price(&x)`, and `Priced::price(&x)` print `pricedT.zero()` and `pricedT.price(x)`, and `T::RATE` prints `pricedT.RATE`. A method is taken from the first of `T`'s bounds whose trait, or one of its supertraits, has it. A call passes the companion of each inferred type argument (`total(items, Item)`, and `Page` for a `Page<u32>`), or its own dictionary on, when its type argument is itself a parameter: the one for that trait, or for a trait that has it among its supertraits (a `T: Named` passes `namedT` where `T: Priced` is asked). The placement is the API (design/07 §9), as `toJson.Page(x, writeT)` is. `impl Tr` in argument position is an anonymous type parameter and prints as one, `Impl1`, `Impl2`, .. in the order written; `impl Tr` in return position and `dyn Tr` (`Box<dyn Tr>`, `&dyn Tr`) are refused: a value has no tag to dispatch on. A struct or enum whose parameters have a user trait bound is refused (bounds on a type are rarely needed in Rust either); an inherent `impl<T: Priced> Page<T>` is accepted, and its methods take the dictionary after their other parameters, as a function does.

Every such const is exported, so a TS caller passes it too; its name is stable API (design/07 §9), and a crate item printed as one, or as a std record's type (`struct Display` beside a `T: Display`), is refused. It is a `BTreeMap` key's comparator wherever §7.19 later widens keys. A type that derives `PartialOrd` alone (as one with a float field must) has no `cmp`, and ordering it stays refused, as `cmp` on floats is (§6.6). `T: Ord` and `T: PartialOrd` carry `{ cmp }`, which orders a `T` as `X.cmp` orders a crate type (`ordT.cmp(a, b).kind === "Less"`, `Ord.max(a, b, ordT.cmp)`, `Ord.option(ordT.cmp)`); `clamp` on a `T` itself is refused, as where its bounds cross std panics with a message that depends on `T`'s type (`min > max. min = 9, max = 1` for an integer or a `char`, `assertion failed: min <= max` for any other), which the dictionary's `cmp` does not carry (`clamp` on an `Option<T>`, whose message is std's one, is accepted); a `T: PartialOrd` is instantiated only at a type that has a `cmp`, so `f64`, `f32`, and a type that derives `PartialOrd` alone are refused at the call; and a primitive's dictionary is a const of the crate (`ordI32`), only the ones used (above). Tested with every pair from sets of structs that differ in the first field or only in a later one, newtypes, a struct with no field, enums of every variant shape, written discriminants (negative, and under `#[repr(u8)]`), a recursive tree through `Box` and `Vec`, a struct that holds the others through `Option`, `Vec`, and a tuple, and non-ASCII text; a hand-written `Ord` whose ties show which of two equals `max`, `min`, `clamp`, iterator `max` / `min`, and a stable `sort` keep; `clamp`'s panic; and an overflow inside a hand-written `cmp`, under `<` and under `sort` (`ordering_derive_equivalence.rs`); the refusals in `check`'s `ordering_derive.rs`; and an ordering shape in the patterns generator (`<` .. `>=` on states and on tuples and `Option`s of events, `cmp` in a `match`, `max`, `min`, `clamp`, `sort`, and iterator `max` / `min`, its types deriving `Ord`).

**`Default`.** `#[derive(Default)]` and a hand-written `impl Default for X { fn default() -> Self }` give the companion `default: (): X`, called by `X::default()`, `Default::default()` where the type is known (an annotated `let`, a parameter, a return, a field), and `..Default::default()` in a struct literal, which is the struct's own whatever the context. The derive gives each field its type's default, in its type's TS form: `0` of the field's width (`0n as I64` for the 64- and 128-bit integers), `0.0`, `false`, `'\0'`, `""`, an empty `Vec`, `BTreeMap`, or `BTreeSet`, `None`, a tuple of defaults, and a crate type's `default()`; on an enum it is the `#[default]` variant, which has no fields. In `X { a, ..Default::default() }` the fields run first, then `default()`, as in Rust. On a type with type parameters the derive's `default` takes a `Default` dictionary per parameter, as its `impl<T: Default>` bounds them (`default: <T>(defaultT: Default<T>): Page<T>`, a field of type `T` `defaultT.default()`); `Page::<u32>::default()` and `Default::default()` at `Page<u32>` pass `defaultU32`, and a `T: Default` instantiated at `Page<u32>` passes the record `{ default: (): Page<U32> => Page.default(defaultU32) }`. `T: Default` carries `{ default }`: `T::default()` and `Default::default()` at a `T` are `defaultT.default()`. Refused: a derive where a field's type has none (`Uuid`, a crate type without `Default`; write `impl Default` with the value), an `impl Default` with any other member or on a type outside the crate, and `Default::default()` whose type is not known where it stands. Tested with every integer width, the floats, `char`, strings, the collections, `Option`, a tuple, nested derived types, an enum's `#[default]` variant, a newtype, a hand-written `default` that panics behind a field that panics first, and `..Default::default()` beside overridden fields (`default_equivalence.rs`).

**`From` and `?`.** `impl From<S> for X`, `X` a struct or enum of the crate and `S` a named type a function may take (a crate type, `ParseIntError`, `uuid::Error`, an integer, a float, `bool`, `char`, `String`, `Uuid`), with `fn from(s: S) -> Self` only, gives `X`'s companion `fromS: (value: S): X`, named after the source type in camel case (`fromParseIntError`, `fromUuidError`, `fromU32`, `fromString`, `fromMyError`): a type may implement `From` for several sources, and one member `from` could hold only one. `X::from(s)`, `From::from(s)` and `s.into()` where the target is known, and `?` on a `Result<_, S>` in a function returning `Result<_, X>` call it: `r?` is `match r { Ok(v) => v, Err(e) => return Err(X.fromS(e)) }`, as `map_err(..)?` is (§7.1), so the conversion runs only on `Err`, after `r`; a `?` whose error types already match prints as before. Refused: a generic source (`impl<T> From<T>`), a source that is an `Option`, a tuple, a reference (`&str`), or has type arguments (`Vec<u8>`), two sources whose members collide (`From<char>` and a crate type `Char`) or a member that meets an inherent method (`from_bool` and `fromBool`), an `impl` on a type outside the crate (`impl From<X> for String`), `impl Into` written by hand, `T: Into<X>` / `T: From<..>` bounds, a conversion into a std type (`let n: u64 = x.into()`), and a `?` whose error type has no `impl From` into the function's, with the message it had, which now names the `impl From` that would take it. `TryFrom` keeps its one member `try_from` (design/02). Tested with `?` over three sources (a crate type, `ParseIntError`, `uuid::Error`) in one function, two `?` in one expression where the first `Err` wins, a conversion that overflows only on `Err`, `map_err(..)?` beside a converting `?`, each spelling of the call, `into()` into a parameter, non-ASCII `String` sources, and an `i64` source at its bounds (`from_equivalence.rs`); and in the statements generator (an error enum with two `impl From`, one function chaining `?` over both in a drawn order).

**Not in this section.** `FromStr` (`s.parse::<X>()`, §6.7 parses integers only); `Iterator` implemented on a crate type; `Hash`; operator traits (`Add`, `Index`). Each is a trait the dispatch above can carry, decided separately.

**Verification.** A fixture per part (`traits.rs`, `display.rs`, `ordering_derive.rs`, `default.rs`, `from.rs`) run against Rust; a trait shape in the statements generator (a trait with a default method, two implementing types, a generic function over it called at both); and `purecrate-ts test`, which calls a generic function with a user trait bound at each crate type that implements all its bounds, rather than at `i32` (§8.4), and says so when none does.

### 8.1 Canonical form

Both sides render values from the same IR types.

- **Rust side.** The test-only proc-macro `purecrate_canon::fixture!` derives `Show` for every fixture type; containers and scalars live in `crates/cli/tests/it/support`.
- **TS side.** The harness generates a printer per type.
- **Form.** It resembles `Debug` (`Order::Placed { lines: Lines::Cons(…), total: Yen(450) }`). Floats are written as their `f64` bit pattern, non-printable-ASCII as `\u{…}`.
- **Why.** Hand-picked projections missed a deliberately injected swap of `expected` and `got` in `OrderError::AmountMismatch`; whole values catch it.

### 8.2 Whole-value arguments

Arguments are whole values too: `fixture!` also derives `Js`, the TS literal of each fixture type, so a case can pass an `Invoice` built in Rust.

Remaining projections:

- Cases routed through a driver returning a scalar compare only what the driver reads (examples/order adds `trace4` to compare the whole final state).
- The counter acceptance test compares only `State.n`.

### 8.3 Coverage

All of this is measured on examples, so equivalence is as strong as the examples' coverage. Where exhaustive enumeration is small, it is used:

- all 1296 sequences for control and vending;
- all 4-step sequences for order and, under each capture and confirmation method, for payment.
### 8.4 A user's crate: `purecrate-ts test`

The differential tests above run on the examples and fixtures. `purecrate-ts test <crate>` runs the same comparison on a user's crate, with no test written by hand:

- **Rust side.** The crate's files are copied with a harness appended to each and compiled by rustc as one binary, with overflow checks and debug assertions on. A file gets `Show` (the canonical form of §8.1) and `Arb` (a value drawn with its TS spelling) for each type it declares, and a case for each function under test it declares, so private fields and the file's own names are all the harness needs.
- **Arguments.** Drawn from each parameter's type with a seed (`--seed`, default 1), `--cases` per function (default 100): integers half the time at the edges of their width, `usize` below 2^53, floats from a list of edges (signed zeros, NaN, infinities, `MAX`) and at random, strings from the crate's own literals, a fixed alphabet (ASCII punctuation, controls, two- to four-byte code points), and runs of two to four characters, lengths often the crate's own small integer literals. Open structs and enums are drawn field by field and variant by variant; a closed type through its public constructors (an associated function, or a free function of its file, returning it, `Result` or `Option` of it), never field by field, and its TS spelling is the constructor call that made it.
- **Type parameters.** A generic function is called with each type parameter at `i32`, which every bound §7.20 takes holds of, one whose bounds carry a dictionary and are all std's (`Ord`, `PartialOrd`, `Display`, `Default`) at `i32` too, the driver writing their records, and one with a crate trait's bound (§7.25) at each public struct or enum of the crate that implements them all and can be drawn (a generic one with its own parameters at `i32`): once for each combination, each reported as a function of its own (`total<Item>`, `total<Coin>`), the TS call passing the type's companion as the dictionary. A function whose bound no such type implements is skipped, and says so.
- **TS side.** The package `build` would write, run by node with a driver that makes each call and prints the result with the printers the differential tests use (`crates/cli/src/difftest/printers.rs`).
- **Result.** Each function is `ok`, `DIFFERS` (the first distinct calls, each with both results; the exit status is 1), or `no cases` when none of a closed parameter's constructors succeeded on drawn input. A function is skipped with the reason when a parameter's type cannot be drawn (a closure, `uuid::Uuid`, a closed type with no constructor).
- **Limits.** A crate that names `uuid::` is refused: rustc gets a stand-in for `uuid`, which parses nothing. Types and modules declared inside an inline `mod x { .. }` are not reached by what is appended at the end of the file. Coverage is what the draws reach: a constructor that needs a checksum (IBAN) or structured text (an RRULE) is seldom satisfied by drawn input, and the functions behind it get no cases.

Run on every example (2026-10-13): no difference. On a crate with `fn double(n: usize) -> usize { n * 2 }` it reports the stated non-equivalence of §3 (Rust goes past 2^53 − 1, the TS `number` throws); `crates/cli/tests/it/test_command.rs` checks both.
